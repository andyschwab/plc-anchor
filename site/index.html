The analogy

atproto identities are a signed, hash-linked log of operations served from one directory. Every op is self-certifying — but a single signature can't tell you whether you were shown the whole history. Email solved the same gap with a layered stack:

PLC ≈ DKIM

Each operation is signed by a then-valid rotation key. Per-op authenticity — already there.

DIDMARC ≈ SPF / DMARC

The layer a signature structurally can't provide: was I shown the complete, current, non-equivocated history? Verified on-chain.

What a directory can do to you

Here is the trap: every operation can be validly signed and the directory can still lie. A signature proves one op is authentic — but the directory alone decides which ops you're shown. A single-operator directory is the chokepoint, and these attacks need no forged key:

Omission

Serve a forked history that quietly drops an operation the DID really signed — rolling an identity back to an attacker-favorable state.

Signatures can't catch it: every op shown is genuinely signed; it's the set that's a lie.

Erasure

Return an empty or 404 audit log for a DID that plainly exists — making an identity simply vanish from a resolver's view.

Signatures can't catch it: nothing served means nothing to verify; absence carries no proof of its own.

Split-view

Show one history to you and a different one to everyone else. Each branch is internally consistent and fully signed — classic equivocation.

Signatures can't catch it: no single viewer holds both halves, so no one can see the fork.

This is the SPF/DMARC-shaped gap that per-op signing (PLC's DKIM layer) structurally leaves open — was I shown the complete, current, non-equivocated history? DIDMARC answers it. Each attack above is a real, ground-truthed scenario in the adversarial report.

How it works

Each opted-in DID's full operation log is re-verified from genesis inside a Starknet contract — the network proves the computation and settles to Ethereum; there is no bespoke prover and no trusted snapshot. The contract commits a proven DID→document root. A resolver fetches a document from the directory and checks it against that root, getting back a status. plc.directory stays canonical; DIDMARC is a read-side witness that anyone turns on alone — the way an email receiver enables DMARC.

The graduated status

  • confirmed — head committed past the 72-hour recovery window; immutable. The strongest assertion.
  • tentative-consistent — the on-chain view agrees with the directory, but the head is still within the recovery window (or explained by clock skew).
  • diverged — the directory's served head contradicts the proven head. This is the alarm that fires on omission and erasure above: warn, quarantine, or refuse to relay.
  • absent — DID not anchored; no opinion (the coverage gap, like DMARC p=none).

Never a false diverged. A directory that's merely running ahead, or a contradiction that plain clock skew could explain, stays at tentative-consistent — not an alarm. A false alarm gets the check switched off, so that restraint is exactly what makes diverged mean something.

Adoption is the DMARC ramp: start by logging the status, then quarantine on diverged, then refuse to relay — each resolver decides on its own.
