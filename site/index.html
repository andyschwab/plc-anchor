The gap a signature leaves

An atproto identity is a signed, hash-linked log of operations, served from a single directory. Every operation is self-certifying, so a signature vouches for the operation it's attached to. It can't tell you whether the directory showed you all of them, the latest ones, or the same ones it showed everyone else.

What a signature proves

This operation is authentic, signed by a key that was valid at the time. PLC already gives you this, per operation.

What it can't

That you were shown the complete, current, and non-equivocated history. No signature can speak for the operations it isn't on, including the ones you never saw.

What a directory can do to you

That gap isn't theoretical. Every operation can be perfectly signed and the directory can still deceive you, because it alone decides which operations you see. None of the attacks below needs a stolen key. All it takes is control of the directory a resolver trusts:

Omission: undo a fix

Your account key is stolen, so you do the right thing and rotate it out with a new signed operation. The directory serves your history with that one operation missing. To the rest of the network the stolen key is still live, and the thief keeps signing as you.

The lie is the operation left out.

Erasure: make someone vanish

The directory simply returns nothing for a DID that plainly exists. Every app that looks the person up sees no such identity. Handles dangle, posts won't resolve, and there's no error to appeal.

Absence carries no proof to check.

Split-view: two faces

Show the victim their real history, while showing one targeted service a forked version that points their account at a server the attacker runs. Neither side ever sees the other's copy.

No one viewer holds both halves.

Each of these is a real, ground-truthed scenario in the adversarial report. DIDMARC is the layer that catches them: independent, on-chain proof of the whole, current history, so a resolver can tell when the directory's answer doesn't add up.

How it works

Each opted-in DID's full operation log lives on Starknet, block-timestamped and append-only. The network proves the record and settles it to Ethereum, so there is no bespoke prover and no trusted snapshot. On the read side the witness re-derives that DID's confirmed head from the on-chain log, fetches the document the directory serves, and compares the two to produce a status. plc.directory stays canonical. DIDMARC is a read-side witness that anyone turns on alone, with no coordination and no protocol change.

The graduated status

  • confirmed: head committed past the 72-hour recovery window, so it's immutable. The strongest assertion.
  • tentative-consistent: the on-chain view agrees with the directory, but the head is still inside the recovery window, or the gap is small enough that clock skew could explain it.
  • diverged: the directory's served head contradicts the proven head. This is the alarm that fires on omission and erasure above: warn, quarantine, or refuse to relay.
  • absent: DID not anchored, so no opinion. DIDMARC has nothing to say about an identity nobody opted in.

Never a false diverged. A directory that's merely running ahead, or a contradiction that plain clock skew could explain, stays at tentative-consistent instead of firing an alarm. A false alarm gets the check switched off, so that restraint is exactly what makes diverged mean something.

Adoption is a ramp. Start by just logging the status, then quarantine on diverged, then refuse to relay. Each resolver decides on its own, at its own pace.

Turn it on

The witness is a small TypeScript library with no external dependencies. Hand it a DID, an anchor reader, and a directory client, and it hands back a status your resolver acts on.

import { check, AnchorReader, DirectoryClient } from "@plc-anchor/witness";

const anchor = AnchorReader.http(process.env.STARKNET_RPC, CONTRACT_ADDR);
const { status, reason } = await check("did:plc:…", anchor, new DirectoryClient());

switch (status) {
  case "confirmed":            // proven and immutable; trust the directory's answer
  case "tentative-consistent": // agrees so far, nothing immutable yet; proceed
  case "absent":               // not anchored; no opinion, resolve as usual
    break;
  case "diverged":             // proven head contradicted; the alarm fired
    quarantine(reason);
}

Prefer the shell? The CLI exits 2 on diverged and 0 otherwise, so it drops straight into a health check or a CI gate:

STARKNET_RPC=https://your-node node cli.ts did:plc:… # [--contract 0x…] [--directory URL]

The ladder is the DMARC ramp: log the status first, then quarantine on diverged, then refuse to relay. Every step is a decision one resolver makes alone.

Adversarial deep-dive

An alarm is only worth having if it fires on real attacks and stays silent on benign disagreement. Both halves are pinned as real signed did:plc chains, run against the shipping witness in the adversarial report. Four worth walking through:

Equivocationdiverged

A mirror serves your history with one confirmed operation quietly omitted. The witness re-derives the confirmed head from the on-chain log and finds it absent from what the directory served. The lie is the operation left out, and the anchor is exactly the second copy that catches it.

Vanishing DIDdiverged

Erasure taken to the limit: the directory returns nothing at all for an anchored DID. The anchor proves the identity exists and its head is confirmed, so an empty answer is a contradiction rather than an absence. The alarm fires where a bare directory would just shrug.

Window-edge skewtentative

The restraint half. A head mismatch that ordinary clock skew near the 72-hour boundary could explain stays tentative-consistent, never an alarm. This is the wall that keeps diverged trustworthy, so no operator ever switches the check off over a false positive.

Anchor self-faulttentative

Even when the anchor's own on-chain log is corrupt and yields no confirmed head, the witness degrades to tentative-consistent. A broken witness declines to accuse an honest directory, which is the only safe direction for the failure to fall.

Write-side attacks fare no better. A forged signature, a weaker-key recovery, and a late recovery can each be paid for and stored on chain permissionlessly, yet the witness's read-side re-derivation drops every one, so a forged operation never reaches a resolver.
